The graphics stack

Who does what on the way to the screen?

A window, a drawing API, and a button solve different problems. See where each belongs and where mojo-ui fits.

On this page

Read the layers by responsibility

Think of drawing and presenting as two jobs. The drawing path produces pixels. The window and display path decides where those pixels appear and delivers input to the app. A toolkit often coordinates both.

  • Windowing and display systems help create windows, route input, and present buffers on screen. On Linux, X11 and Wayland are ways clients talk to a display server or compositor. On Windows, Win32 exposes window and input APIs and DWM composes windows. On macOS, Cocoa’s AppKit handles app windows and events, with system services handling composition.
  • Graphics APIs describe work for a graphics implementation. OpenGL, Vulkan, Direct3D (the 3D graphics API in Microsoft’s DirectX family), Metal, and WebGPU can submit drawing to a GPU. A software implementation can execute graphics work on the CPU.
  • 2D libraries such as Skia, Direct2D, and Cairo work with concepts like paths, glyphs, and images. They may use CPU rendering, hardware acceleration, or both, depending on the library and backend.
  • UI toolkits such as GPUI, egui, Dear ImGui, and Qt provide widgets and layout. Some own an event loop and others leave it to the host. Their rendering integrations vary.

X11 and Direct3D solve different jobs. X11 concerns windows, input, and presenting pixels on Linux. Direct3D draws through Microsoft’s graphics API, usually on a GPU. An X11 program can display a CPU surface without Direct3D. This demo draws without X11 and saves a file instead.

CPU rendering, GPU rendering, and drivers

In CPU rendering, your loops calculate the pixel colors in system memory. In GPU rendering, the app describes resources and drawing or compute work, and the GPU runs that work across many hardware lanes. Both can produce the same picture.

A GPU driver implements parts of the graphics API for the device. It helps turn work requests into device commands and manages resources and synchronization with the operating system and GPU. The display system can then present the result, often through a compositor that combines multiple windows into a screen image.

For a small image, submitting work or copying memory can cost more than the drawing saves. A large scene with lots of independent pixel work is a better place to test GPU rendering.

What SDL and GLFW would add

SDL and GLFW can open a window and receive input on several platforms. SDL also offers a 2D rendering API that can display a texture made from CPU pixels. GLFW can provide an OpenGL context or help create a Vulkan surface. Your renderer or graphics code still turns shapes into pixels.

For mojo-ui, the first window host could show the CPU framebuffer as-is. Stack, Label, and Button would draw the familiar demo. The host would present the resulting pixels each time it draws a frame.
