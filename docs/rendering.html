Rendering 101

How shapes become pixels

Start with a grid of pixels, then build up to shapes, transparent layers, text, and layout.

A pixel has an address

A pixel is one sample on the image grid. A framebuffer stores those samples in memory. The demo’s 480 × 248 framebuffer holds 119,040 colors. The upper-left pixel is (0, 0).

The grid has two coordinates, but the list has one index. Each row occupies width entries. In a 4-pixel-wide image, (2, 1) is index 1 × 4 + 2 = 6. Walking left to right touches neighboring entries, which will matter when you look at CPU caches.

Try drawing Rect(2, 1, 3, 2) on paper. It covers columns 2, 3, and 4 and rows 1 and 2. On a framebuffer only four pixels wide, clipping also removes column 4.

Rasterization and coverage

Rasterization answers a practical question for every shape. Which pixels should this shape touch? For a rectangle aligned to the grid, that is a pair of integer ranges. For a line, the renderer steps along the dominant axis and picks a nearby pixel on the other axis.

A rounded corner cuts through some pixel squares. fill_rounded_rect checks one point per square, its center at (x + 0.5, y + 0.5). A center on or inside the radius gets the full source color and alpha. A center outside gets skipped. At low resolution this gives the corner a staircase edge.

One easy experiment is to test four points within each pixel and count how many are inside. Four samples cost more than one, but they give you intermediate coverage values and a smoother edge.

Put one color over another

Alpha says how opaque a color is. With straight alpha, red can be stored as Color(255, 0, 0, 128). Its red channel remains 255 even though its opacity is about half.

Color.over treats the new color as the source and the existing pixel as the background. A transparent source leaves the pixel alone. An opaque one replaces it. Otherwise the background contributes only through the part that the source lets show, scaled by the background’s own alpha.

Try that half-opaque red over opaque blue. Roughly half the blue shows through and the result is Color(128, 0, 127, 255). With half-opaque blue underneath, the result is Color(170, 0, 85, 192). The code accumulates integer weights, divides the color channels by the combined weight to return straight-alpha values, and rounds the channel and alpha divisions.

Drawing order matters. Paint blue over red and you get a different result. This is also why the inside border avoids drawing a corner twice.

Characters, glyphs, and spacing

A character is part of the text. A glyph is the shape a font uses to draw it. In this renderer, the glyph is a bitmap. The bits in the first row of A, 01110, paint the middle three of its five pixels.

At scale 1 a glyph takes up five columns, and the next glyph starts six columns after it. At scale 2, every on bit becomes a 2 × 2 block. Two glyphs at scale 2 occupy 22 pixels because the last glyph needs no trailing gap.

Scalable TrueType fonts can store curves that are rasterized at a chosen size. A shaper such as HarfBuzz maps a run of text to positioned glyphs. For example, it can pick the connected forms of Persian letters and position marks relative to their bases. The repo’s draw_text walks code points and looks up one fixed bitmap each time. Its font has no shaping support.

Give each widget a box

Preferred size is the space a widget asks for. A label measures the text and its height. A button asks for the label’s size plus its own padding. The parent gets to decide how much of that request fits.

In the demo, the vertical stack starts 24 pixels inside the panel on each side. The title’s preferred height is 28 pixels at scale 4. After placing it, the cursor moves down those 28 pixels plus 12 pixels of spacing. The next label starts there. Later a horizontal stack places the buttons left to right.

Padding is room inside an edge. Spacing is the gap between siblings. Clipping limits where they can draw.

What an event loop would do

The demo runs through its draw calls once, saves the PNG, and returns. A windowed version would create a window and repeat this cycle until you close it:

  1. Poll or wait for window messages, keyboard events, and pointer events.
  2. Update application state. A future button would compare the pointer position with its bounds before reacting to a press.
  3. Lay out and draw the current frame when needed, then present its pixels to the window.

The host would own the loop. The existing drawing calls can already produce the pixels for one pass through it.
