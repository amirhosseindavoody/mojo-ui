Hands-on exercises

Build on the rasterizer

First measure the code you have. Then try one change at a time, check the pixels, and measure again.

On this page

Run these from the repository root. Create the named programs in your own exercises/ directory as you go. Use -I src when you only need public APIs. For work inside the renderer, copy src/mojo_ui to exercises/sandbox/mojo_ui and use -I exercises/sandbox.

Keep pixi run test as the check for the original library. Run the existing test program against your sandbox too when you expect identical pixels.

pixi run test
pixi run mojo run -I exercises/sandbox tests/test_mojo_ui.mojo

1. Time a fill and a frame

Goal. Get a baseline you can reproduce. You’ll practice warm-up, choosing a workload, and checking what the timer actually includes.

Start here. Read Framebuffer.fill_rect in src/mojo_ui/raster.mojo and the draw sequence in examples/demo.mojo. Allocate the frame once. With perf_counter_ns from std.time, bracket a batch of fills, subtract the start from the end, and divide by the number of fills. Read or check pixels after the timed batch so the result is used. Warm up with a few batches and print the median and range of repeated measurements.

Measure success. Report nanoseconds per fill or pixels per second for opaque and translucent fills at 480 × 248 and at a larger size. Hold the frame dimensions, input colors, and workload fixed when comparing implementations. Time rendering a full frame separately from write_png so file I/O and encoding don’t hide changes to drawing. Lower time for the same work is faster. Record machine and toolchain with your results.

pixi run mojo run -I src exercises/bench_fill.mojo

2. SIMD-ize the rectangle fill

Goal. Write several adjacent pixels per batch in the opaque case. You’ll practice lanes, contiguous stores, and finishing the last few pixels in a row.

Start here. Follow fill_rect to _blend_at. Keep the intersection with framebuffer bounds. Prototype row stores over a packed pixel scratch buffer first if that makes the pixel format easier to control. Broadcast the opaque source word across vector lanes, write only inside the clipped row, then handle its tail. Keep the existing blend for translucent colors. Try the same repeated stores in clear, including for a transparent clear.

Measure success. Compare with the scalar reference after each draw. Include widths 1, 7, 8, and 9, a partially offscreen rectangle, alpha values 0, 128, and 255, and a partially transparent destination. Profile with the baseline workload and report whether throughput improved.

pixi run mojo run -I exercises/sandbox exercises/simd_fill.mojo
pixi run mojo run -I exercises/sandbox tests/test_mojo_ui.mojo

3. Divide the frame into parallel tiles

Goal. Use multiple cores to fill disjoint parts of a frame. You’ll practice splitting work, assigning write ownership, and joining workers before consuming their output.

Start here. Reuse Rect.intersection and the row loop in fill_rect. Start with serial 64 × 64 tiles, including smaller tiles at the edges. Then give groups of tiles to separate workers. Use one private framebuffer per worker to avoid sharing a mutable List while you learn. Translate bounds into local coordinates and assemble the returned pixels after the workers finish. If you don’t have a verified Mojo worker API, you can try a Python process pool with a compiled Mojo worker that accepts a tile’s bounds and returns its bytes. Keep the same draw order inside every tile when you add overlapping draws.

Measure success. Compare every pixel against the untiled fill after a clear and after two overlapping fills with alpha. Try a width one pixel beyond an exact tile multiple. Measure one worker and several workers at the demo size and a larger size, including the cost of dispatching and joining. If you use private buffers, include the copy when reporting end-to-end time.

pixi run mojo run -I exercises/sandbox exercises/tiled_fill.mojo

Use that program as the serial tiled reference. For the Python process variant, build your worker once, then have your local Python run the worker executable and compare the combined output with that reference.

pixi run mojo build -I exercises/sandbox exercises/tile_worker.mojo -o exercises/tile_worker
python3 exercises/parallel_tiles.py

4. Smooth a rounded edge

Goal. Add an experimental anti-aliased rounded rectangle. You’ll practice estimating coverage and carrying it into source alpha.

Start here. In fill_rounded_rect, replace the center sample in your experimental path with four samples. Try offsets 0.25 and 0.75 on each axis. Multiply source alpha by the fraction inside, round to a byte, and use Color.over once per destination pixel. Keep the hard-edged method as a reference.

Measure success. Write two PNGs on the same contrasting background. Zoom in with nearest-neighbor scaling. Look for intermediate shades at the corners, and check that fully covered and fully uncovered pixels match the original. Record the time cost on a rounded panel. Once that works, try the same coverage idea on a line with a defined width.

pixi run mojo run -I exercises/sandbox exercises/rounded_aa.mojo

5. Render a TrueType glyph

Goal. Draw a scalable glyph into the framebuffer. You’ll practice turning an outline into a coverage mask and positioning it relative to a baseline.

Start here. Read _glyph in src/mojo_ui/font.mojo and the row walk in draw_text. Pick a font you can use locally. Use FreeType or a small native helper to rasterize one TrueType outline at a chosen size. Use its advance to move the pen and its bearings to position the mask. Treat each mask byte as coverage when blending the chosen color. The existing clip logic is a good pattern to reuse.

Measure success. Draw two glyphs at two sizes in a PNG and check alignment, clipping, and partially covered edges. As an extension, cache masks by glyph ID and size in a small atlas, a shared image holding many glyphs. Compare repeated drawing with and without the cache. For shaped text, a separate step would use HarfBuzz to get glyph IDs and positions. One or two glyphs are enough for this exercise.

pixi run mojo run -I exercises/sandbox exercises/outline_text.mojo

6. Present a frame in an SDL window

Goal. Show the CPU-rendered demo in a real window. You’ll practice C FFI, pixel formats, row pitch, and resource lifetimes.

Start here. Install SDL3 for your platform and use its headers and official docs to check the C signatures. Wrap a small surface of SDL calls through Mojo’s C FFI or a thin C shim. Reuse the draw sequence in examples/demo.mojo, then stage four explicit RGBA bytes per pixel using Framebuffer.pixel. Match SDL’s texture format to the byte order in that buffer and pass a pitch of 4 × width for tightly packed rows.

Measure success. Open a window, update the texture, draw it, and present it. Compare colors and orientation with pixi run example. Pump window events so you can close the window, and check that you release the texture, renderer, and window on exit. Leave button interaction for a later exercise. Time staging and upload separately if you want to see where presentation spends time.

pixi run example
pixi run mojo run -I src exercises/sdl_window.mojo

7. Sketch a GPU backend

Goal. Plan a backend boundary and try a small proof of concept on supported hardware. You’ll learn what belongs in CPU layout, what you transfer, and what a GPU kernel or drawing pass does.

Start here. Follow Stack.place to Framebuffer.fill_rect. Keep the layout rectangles on the CPU. Sketch a representation for a rectangle, clip, and color that a backend could consume. First show an uploaded CPU-rendered frame. Then try filling one rectangle in an offscreen GPU image with one invocation per pixel and read it back for comparison. Multiple draws will need ordering rules for blending.

Measure success. Generate a CPU reference for a clipped opaque rectangle and compare the GPU readback pixel by pixel. Time uploads, completed kernel work, and readback separately. A timer around submission alone measures the host’s work of asking for a draw. With no compatible GPU, finish the backend sketch and use the CPU reference to document expected pixels and transfer sizes.

pixi run mojo run -I src exercises/gpu_reference.mojo
pixi run mojo run -I src exercises/gpu_rect.mojo

The first command is the CPU harness you write. The second is for the optional prototype and needs a compatible Mojo GPU toolchain and device.
