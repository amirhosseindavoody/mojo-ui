Read a little Mojo at a time

A Mojo struct groups fields and methods, much like a Rust struct with an impl. Mojo uses indentation like Python, and declarations such as var _width: Int give fields a type. Framebuffer owns its list and implements Movable so ownership of the framebuffer can be transferred.

mut frame: Framebuffer in a widget’s draw lets the widget change the caller’s existing framebuffer. Think of a Rust &mut borrow as an analogy. Mojo has its own argument conventions and lifetime rules. A mut self method does the same for the receiver. The caller can keep drawing into the same buffer.

In Label.__init__, out self is the instance being initialized. The var text parameter gives the function an owned value. text^ transfers that value into the label field, leaving the local text unavailable until assigned again. This avoids copying the string for that assignment.

Use the same idea when writing an exercise. Allocate the framebuffer once and draw into it many times. Passing it for mutation lets you avoid allocating or copying a frame for each widget.

Keep nearby pixels nearby

CPU caches hold recently accessed blocks of memory. When the CPU fetches one pixel, bytes near it tend to arrive in the same cache line. The inner x loop of fill_rect already follows the list order. Walking a tall column would step by an entire row each time and use less of each cache line before fetching another.

List[Color] is an array of structs, or AoS. Red, green, blue, and alpha for each pixel are interleaved as fields. It puts everything Color.over needs for one pixel together.

  • Structure of arrays (SoA). Separate red, green, blue, and alpha arrays give you contiguous values of each channel. A vector blend can load several red values together. Whole-frame passes that touch every channel now have four streams, and PNG or texture upload needs interleaved bytes again.
  • Packed pixels. A List[UInt32] can store one explicit 32-bit word per pixel. Several identical words can be written together for an opaque fill or clear. Blending requires unpacking channels, and byte order matters when those words cross a C or graphics boundary.

The current Color fields are already byte-sized. Treat packing or SoA as a change in how you access bytes, with any cache or SIMD gain to be measured. If you draw several primitives per region, a tile can keep its rows hot in cache while you finish that region.

Work on several pixels in one instruction

SIMD means single instruction, multiple data. A vector has lanes. If you add two vectors, each lane gets its own sum. The font gives you a readable first encounter with Mojo’s type syntax:

Read the brackets as a compile-time recipe for the type. It holds eight unsigned bytes. This renderer uses the lanes as storage for glyph rows and indexes them one at a time. The glyph buffer itself doesn’t make text drawing a SIMD operation.

For an opaque fill_rect, every covered destination can receive the source directly. Once the rectangle is clipped, write a vector of repeated pixel words across each row. Finish the last few pixels with smaller batches or a scalar loop. clear can also write repeated words, even when its input is transparent, because its job is replacement.

For a translucent fill, load the destination pixels too. Match Color.over by widening the channels before multiplying, preserving the integer rounding, and handling fully transparent source or destination colors. Start with the opaque case so you can measure the gain from vector stores before implementing the blend.

Checked on Mojo 1.2.0. vectorize imports from std.algorithm. A small toolchain check used nine items, a requested width of four, and a callback parameterized by lane count. The callback received offsets 0, 4, and 8 with widths 4, 4, and 1. The callback still has to do the vector work. The compiler, CPU, and your data layout determine which instructions run.

Give separate tiles to separate cores

SIMD uses several lanes within an instruction. CPU parallelism lets multiple cores run work at the same time. Divide the frame into disjoint tiles, such as 64 × 64 pixels. Intersect each rectangle with a tile and redraw the clipped portion there. If you process several draws inside a tile, keep them in their original order so alpha still blends correctly.

Start with clear or an opaque fill. Each output pixel has a single writer. Have workers finish before you read the frame or write the PNG. In a tightly packed buffer, workers writing adjacent tiles can still contend for a shared cache line. Compare a tile grid with whole-row bands to see how much work and memory traffic each approach creates.

The demo’s frame may be too small to repay worker startup and synchronization. Test a larger buffer as well. A parallelize import could not be verified with the locked Mojo 1.2.0 toolchain. Check the official standard library for the version you run before choosing a worker API. The tiling exercise can use a serial pass and a worker path with independent buffers.

Cross into C with a small interface

A pointer represents a memory address. Pointers make it possible for C and Mojo to refer to the same pixel bytes. The moment you use an unsafe pointer, you must prove the address is valid, the range and alignment are right, the buffer stays alive, and concurrent access is safe. A stale or out-of-bounds pointer can corrupt memory.

A foreign function interface (FFI) lets Mojo call a C library using the types and calling convention that C expects. With SDL, a window host could first read Framebuffer.pixel in row order and produce explicit RGBA bytes. Then it could hand SDL a pointer to those bytes and the row pitch in bytes. A tightly packed RGBA byte buffer has a pitch of 4 × width.

Keep the buffer alive for the call and obey the receiving API’s lifetime rules. Start with the copy so the pixel format is easy to verify. A later host could use a borrow or write directly into an SDL texture buffer, after checking layout, pitch, and ownership. See the official Mojo C FFI guide for the current syntax.

Move the image first, then the drawing

The first GPU-shaped step is still CPU rendering. Upload the RGBA buffer to a texture and display it through a graphics API or SDL. This proves presentation and gives you a number for the cost of the upload. The CPU still does all the blending.

A later GPU backend could keep layout on the CPU and pass rectangles, colors, and clips to the device. The GPU could rasterize them through a graphics pipeline or use a compute kernel with many invocations, each handling a pixel or tile. Respect draw order for overlapping transparent shapes and match the CPU’s straight-alpha and rounding rules if you need byte-for-byte parity.

Mojo can target GPU kernels with a compatible toolchain and device. The host-side APIs, supported hardware, and interop with display textures can change. Check the locked version and available device before relying on a specific API. Start with one offscreen rectangle and measure upload, kernel execution, and readback separately.
